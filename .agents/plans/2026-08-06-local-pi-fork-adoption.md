# Adopt the bac2qh/pi Fork in Pi Web

Status: approved

## Objective

Adopt the local `bac2qh/pi` fork at exact commit `734502cb86eaf631e1ceeb403dbd717e3b78404f` in Pi Web without changing the global Pi installation or publishing the fork artifact remotely. Package the fork locally with an unambiguous `@bac2qh/pi-coding-agent@0.84.0-bac2qh.734502cb8` identity, move compatible official companion Pi dependencies from `0.82.1` to the `0.84.0` line, preserve Pi Web's existing behavior and project-specific integrations, and define a repeatable local dependency workflow based on the sibling fork checkout.

Success means Pi Web loads the forked coding-agent implementation rather than the same-version upstream registry package, its Pi-facing compile/test/runtime contracts still pass, npm records a coherent `0.84.0` companion graph, the byte-identical local tarball can be rebuilt and reinstalled from the exact fork commit, and `/opt/homebrew/bin/pi` plus all real user Pi package/configuration/session state remain unchanged.

## Design / Implementation Strategy

1. Add a standard-library-only local helper (expected path: `scripts/build-local-pi-fork.mjs`) that verifies the sibling fork and exact Git object, then materializes a disposable source tree from `734502cb86eaf631e1ceeb403dbd717e3b78404f`, never from the moving checkout contents. Pin the reproducibility environment to the validated Node `24.19.0` and npm `11.17.0`, hydrate with `npm ci --ignore-scripts`, run the fork's checks/tests/build path, and use its local-release machinery outside both source repositories; do not install anything globally.
2. After the exact source build passes, create a disposable packaging stage for coding-agent and apply only a declared identity overlay: set `package.json` name/version/repository/source-commit metadata plus the shrinkwrap top-level and `packages[""]` name/version to `@bac2qh/pi-coding-agent@0.84.0-bac2qh.734502cb8` and `bac2qh/pi`/the full source commit. Keep runtime code and dependency ranges byte-equivalent to the built target. Pack with scripts disabled to the fork-ignored path `../pi/.artifacts/pi-web/734502cb8/bac2qh-pi-coding-agent-0.84.0-bac2qh.734502cb8.tgz` as resolved from the retained Pi Web main checkout.
3. Prove artifact identity and byte reproducibility before adoption: independently build/pack twice from fresh exact-commit source and staging directories under the pinned toolchain, require identical SHA-512 and SHA-256 digests, and inspect package name/version/provenance, `dist`, matching shrinkwrap root, and file list. Confirm each source build resolves to the exact commit and each staging delta is metadata-only. Any byte mismatch blocks; content-only equivalence is insufficient because `package-lock.json` pins tarball integrity. The fork differs from upstream `v0.84.0` only in coding-agent implementation/tests/docs for between-tool-turn compaction, so use official registry `0.84.0` artifacts for unchanged companion packages.
4. Set the existing `@earendil-works/pi-coding-agent` compatibility key to `file:../pi/.artifacts/pi-web/734502cb8/bac2qh-pi-coding-agent-0.84.0-bac2qh.734502cb8.tgz`. Advance direct `@earendil-works/pi-ai` and `@earendil-works/pi-tui` intent to `^0.84.0`, preserving Pi Web's established imports and npm manifest style while requiring exact `0.84.0` companion lock resolution. The tarball must install packaged `dist` plus the coding-agent shrinkwrap and record npm integrity; do not use a live source-directory symlink.
5. Regenerate `package-lock.json` through npm with scripts disabled and validate the local tarball resolution and explicit npm alias presentation. Do not hand-edit the lock, resolve coding-agent from the registry, or broaden the npm-authoritative scope to the currently unvalidated `bun.lock`.
6. Reconcile compile-time or runtime API drift only where evidence requires it. In particular, verify Pi `0.84.0`'s delta-only `message_update` contract, auth/model refresh changes, TypeBox upgrade, session APIs, and the fork's in-run `compaction_start`/`compaction_end` behavior against Pi Web-owned projection, settlement accounting, clone, hosted implementation, auth, plugin, skill, and custom-server contracts. Add an installed-artifact integration probe: drive the packaged fork through its faux provider and pass the actual sanitized native event trace—including compaction and final `agent_settled` ordering—through `AgentSessionWrapper`, or exercise the packaged `AgentSession` directly inside the wrapper if the public construction seam permits. Assert no projected/global idle before true native settlement. Preserve Pi Web behavior rather than replacing it with stock Pi behavior.
7. Validate the selected local dependency through source/artifact identity inspection, the exact `0.84.0` companion graph, TypeScript, lint, focused Pi boundary suites, the complete existing Node suite, and bounded development startup/session smoke coverage. Exercise the fork's between-turn compaction with its faux-provider regression rather than a paid provider.
8. Prove the documented local rehydration path from a clean Pi Web install plus the exact sibling fork commit. It must rebuild and reinstall without custom GitHub/npm publication or global installation and must fail clearly when the fork checkout, exact Git object, pinned toolchain, metadata overlay, or local artifact is missing or mismatched. Update English/Chinese development instructions and add an explicit `docs/release.md` warning that this manifest is local-only and non-publishable, while leaving the release command and implementation unchanged.

## Assumptions, Risks, and Blockers

- The selected tarball is intentionally machine-layout-dependent and untracked. `npm ci` fails until the sibling fork artifact is generated; the setup helper and error message must name that prerequisite without downloading or substituting coding-agent.
- npm treats `dependencies` as references, not files to embed automatically. A bounded pack/install probe confirmed that packing an application preserves its `file:../...tgz` dependency text, does not include the external dependency tarball, and a consumer install then fails `ENOENT` while looking for that relative file in the consumer's install tree. Local Pi Web install is valid because the sibling artifact exists; npm publication of this same manifest is not self-contained.
- The final relative path naturally resolves from retained Pi Web main but not from nested managed worktrees. Generate the final npm lock and run decisive clean-install validation in disposable runtime state that reproduces the sibling layout; do not alter main before closeout or create a fake registered worktree.
- Artifact creation must not overwrite unrelated `.agents/runtime` or fork `.artifacts` state. Build to task-owned temporary paths, compare both independent artifacts, then atomically publish only the verified byte-identical tarball into the exact commit-addressed subdirectory; remove only task-owned temporary state.
- Byte-identical packing is a hard blocker because the committed npm integrity is over compressed tarball bytes. Toolchain pinning may not be sufficient if generated model data, timestamps, ordering, locale, timezone, or platform leak into output; identify and eliminate such inputs rather than accepting content-only equivalence.
- **User decision (2026-08-06):** leave `npm run release` and its implementation untouched. Local install/build/start does not use it. Document that the local-fork manifest is intentionally non-publishable; accidental publication would preserve the unresolved `file:` reference and produce a broken consumer install.
- Pi `0.84.0` public API/event changes may require Pi Web compatibility edits. Any material architecture change or loss of Pi Web-owned behavior is scope growth and requires stopping for a follow-up plan rather than broad adaptation.
- Provider-authenticated end-to-end calls are not required for the fork-specific behavior and must not expose credentials. If a separate live-provider smoke is desired, treat it as explicit manual validation with sanitized evidence.
- Existing unrelated working-tree changes—including other draft plans and runtime artifacts—must remain untouched.
