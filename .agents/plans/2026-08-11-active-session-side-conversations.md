# Active-Session Side Conversations

Status: approved
Date: 2026-08-11

## Objective

Add a distinct `/side` command that snapshots the live source branch, extracts its latest structurally safe prefix into a normal durable Pi session, names that child `side-conversation-<timestamp>`, and selects it while the source turn continues unchanged. Existing `/clone` remains a separate duplicate-and-stay operation.

Success means:

- `/side` has one clear snapshot-clone-and-switch contract rather than timing-dependent `/clone` behavior.
- The child receives an immutable, internally consistent invocation-time prefix without maintaining a moving safe-leaf watermark on the source wrapper.
- An unresolved tool-call message and its partial result batch are excluded together; completed prior context is retained.
- The source session keeps running and remains unchanged.
- The child is a durable multi-turn Pi session intended primarily for investigation. It keeps ordinary Pi Web inspection and workspace tools, but hard-removes known subagent and session-launching extensions; Codex-equivalent side instructions treat inherited work as reference-only and discourage source mutation unless a new side prompt explicitly requests it.
- The model retains the inherited safe prefix, but the ordinary browser chat transcript starts after the side boundary and renders neither inherited messages nor the host boundary marker. The existing explicit **Full history** HTML export remains an intentional complete-native-file view and may show that inherited prefix.
- The child appears immediately as an ordinary child in the existing session tree, becomes the focused session, persists indefinitely, and is removed from normal view only through the existing manual Hide workflow.
- Returning to the source works either through ordinary session-tree navigation or a side-only **Return to parent** button in the chat top bar; neither path discards, deletes, hides, or otherwise cleans up the side child.
- A side session is a terminal session-derivation node: no Pi-Web-owned operation may copy its boundary or context into another session. Nested `/side`, existing `/clone`, and Fork / New session are unavailable from it, with server enforcement rather than UI-only hiding; same-file Edit from here remains allowed.
- Existing idle `/clone`, Fork / New session, in-session branch, and Hide/Restore behavior remain correct for ordinary sessions.

## Design / Implementation Strategy

Investigation established that the idle restriction is Pi-Web-owned, not a restriction in `SessionManager.createBranchedSession()`. Native interactive Pi accepts `/clone` while streaming, but it implements clone as a replacement-session fork: it creates the branch, tears down and aborts the old runtime when necessary, emits replacement lifecycle events, and switches to the clone. That does **not** satisfy this feature because the source run cannot continue. Pi Web must retain its disposable-manager extraction boundary and must never invoke native runtime replacement on the source.

Current Pi Web `/clone` is therefore not a textual pass-through. Pi's command is owned by terminal `InteractiveMode`, outside `AgentSession.prompt()` and the RPC-visible extension-command list. Pi Web intercepts exact `/clone`, sends a host RPC command with the displayed leaf, rejects active/stale/unmaterialized sources, and invokes only Pi's lower-level `SessionManager.createBranchedSession()` on a disposable reopened manager. It verifies and publishes the native child, refreshes the sidebar, and deliberately stays on the source without emitting Pi's replacement lifecycle. `/side` should reuse that native extraction adapter with a server-computed safe cutoff, generated name, active-run eligibility, and child selection—not attempt to forward `/side` or `/clone` into the source agent.

Pi writes complete messages on `message_end`; partial assistant streaming is not persisted. A Pi `turn_end` occurs only after the assistant message and every tool result for that turn have completed, so the source leaf observed at a completed `turn_end` is a promising coherent cut point. The physical latest persisted leaf is not sufficient: during tool execution it can be an assistant message containing tool calls whose tool results do not exist yet. Before a first session has any assistant message, Pi may also defer materializing the JSONL file, so an early first-turn side branch can legitimately have no extractable persisted prefix.

`/side` synchronously captures `liveLeafId` and one `sessionManager.getBranch(liveLeafId)` array when invoked and computes the cutoff only from that immutable entry-ID snapshot; it does not maintain a moving source watermark or reread the live leaf during analysis. Partial assistant stream deltas are not session entries, so ordinary streaming naturally snapshots through the latest complete entry. The active user prompt is retained in that case as inherited reference context; the targeted side boundary, rather than truncation before the prompt, prevents it from becoming the child's active task. If the snapshot contains an assistant message with tool calls that do not yet all have matching persisted tool-result messages, the cutoff is that assistant entry's parent. For a multi-call assistant batch, the whole assistant message and every already-persisted partial result from that batch must be excluded together because Pi represents all calls in one assistant message. Tool-call normalization is strict: call IDs must be non-empty and unique, result IDs must form an exact one-to-one set, and duplicate, empty, malformed, or foreign IDs produce a bounded normalization refusal rather than a guessed cutoff. Once every result in the batch exists, the completed batch is eligible.

The selected entry is passed to the existing disposable-manager native extraction boundary. After `createBranchedSession(cutoffId)` returns a materialized candidate, reopen it, derive its authoritative native ID, append the bounded hidden side boundary, append ordinary Pi session-name metadata, and reopen once more to verify a distinct ID, native parent, exact single targeted marker, and generated name. This entire finalization is pre-publication: any extraction, marker, naming, or verification failure cleans up only the unadvertised candidate before path caching, list invalidation/notification, RPC success, or browser selection. The verified child is then cached/discovered normally under native `parentSession` ancestry and immediately selected without shutting down the source wrapper. The page-owned session view transport retains the hidden source while it is active. Returning means either selecting the parent row through the existing session tree or activating a side-only **Return to parent** control in the chat top bar; both use the same ordinary session-selection path. The root session read should derive bounded side metadata from the targeted boundary and expose the already-supported resolved native `parentSessionId` so the control does not infer side identity from a mutable display name. The button prepares selection immediately, hydrates the complete parent from `/api/sessions` (including a hidden parent), and uses the existing selected-ID/generation guards so a delayed lookup cannot steal a newer selection. If the native parent cannot be resolved, show a bounded disabled/unavailable state rather than guessing. The durable child remains discoverable until the user manually applies existing Hide. There is no automatic discard, deletion, hiding, expiry, temporary runtime, or side cleanup, and the Return control performs no mutation. No child-only synthetic tool result, abort marker, custom session format, or overlay is required.

The command and lifecycle decisions are fixed: only exact trimmed `/side` is a host command; inline `/side <question>` is intentionally out of scope. `/side` supersedes the interim `/btw` spelling, `/clone` remains unchanged for ordinary sessions, and `/side` creates a durable multi-turn investigative child. It retains ordinary read/search/web/browser and workspace tools, including mutation tools, but changes the earlier normal-tools default by hard-removing known subagent and session-launching extensions. Detect side mode from the targeted marker before `createAgentSessionServices()`. Use a resource-loader extension override with an exact bounded registration classifier: fail closed and omit the whole loaded extension when it registers the exact `subagent` execution tool or any of `start-implementation`, `open-implementation`, and `orchestrate-implementation`; preserve nonmatching extensions. Pass a defensive SDK `excludeTools` set containing the known delegation channel names (`subagent`, `subagent_wait`, `subagent_supervisor`, and `intercom`) so malformed requests and active-tool reconstruction cannot re-enable them. Filtering the complete extension—not merely its visible command/tool—removes that extension's commands and natural-input handlers and is reapplied on resource reload. Extension factories necessarily evaluate before `extensionsOverride`; the guarantee is removal of their runtime registrations, not prevention of module initialization side effects. `get_tools`, `set_tools`, `get_commands`, reload, and browser controls must never re-enable or advertise an excluded capability. Bounded diagnostics may report only matched registration classes/source kinds, never full extension paths. Do not modify those external extensions or the Pi fork.

The remaining mutation policy is Codex-equivalent rather than hard read-only: persistent side-boundary context and a stronger side-mode system/developer instruction must say that inherited instructions, plans, tool calls, and approvals are reference-only; non-mutating inspection is preferred; and source/workspace mutation is allowed only when a user explicitly requests it after the side boundary. Subagent/session recurrence is a capability restriction as well as an instruction; filesystem mutation remains model policy plus ordinary Pi permissions, not sandbox enforcement. Because unrestricted `bash` can execute arbitrary user commands, the hard guarantee covers Pi Web and the known loaded session-launch facilities, not a hostile shell script that directly writes native session files.

The native child should carry one bounded reserved Pi `custom_message` side-boundary entry whose static content participates in model context and whose strict details contain only the supported policy version and exact target child session ID. A pure classifier scans raw entries independently of the currently selected leaf: no reserved marker means ordinary; exactly one well-formed marker targeting this session means side; a copied marker targeting another ID does not confer side identity; and malformed, unsupported, duplicate, or conflicting reserved state fails closed rather than choosing a boundary. For a valid side, the current/selected raw branch must contain that exact marker. Root/context requests and wrapper or extension navigation to the marker's ancestors or any non-descendant return a bounded side-boundary refusal; same-file navigation remains available only inside the marker-rooted subtree.

Pi Web suppresses both the host marker and every inherited pre-boundary message from child presentation. A shared raw-branch-aware projection helper filters compaction-aware UI `messages`/`entryIds` by entry ancestry strictly after the marker and projects the branch tree from the marker's children. Because a post-boundary compaction summary can mix inherited and side material, side presentation renders only a generic compaction notice rather than summary text; native/model context remains Pi's complete compaction-aware context. The mandatory side system-prompt suffix explicitly treats inherited content and compaction summaries as reference-only, survives startup, active-tool changes, manual/automatic compaction, reload, reopen, restart, and the tools-off preset, and is injected idempotently through the side-specific resource loader rather than mutating native Pi persistence. Root load establishes side identity before live effects are accepted; subsequent projected messages are necessarily post-boundary, while every HTTP root/context repair remains the canonical filtered convergence path. Copied markers whose target session ID does not match do not silently convert unrelated descendants into side mode. This preserves Codex's model-visible/UI-hidden inheritance without adding a separate persistence file.

`/side` is eligible whether the source is active or already idle when the command is handled. It always snapshots the then-current live manager and applies the same cutoff rule, avoiding a completion race that would otherwise turn a valid command into a busy/idle mismatch. A session whose exact targeted side marker identifies its own session ID is terminal for derivation: it cannot invoke `/side`, existing `/clone`, or Fork / New session, and its runtime does not load known subagent or Start/Orchestrate session-launching extensions. The wrapper must enforce the host-command prohibitions and marker-descendant navigation for direct RPC and extension context actions; SDK/resource construction must enforce capability removal; the client must return bounded explanatory outcomes for exact commands; and side presentation must omit the per-message Fork / New session action. Neither copied-marker ambiguity nor navigation enforcement may be left to UI hiding alone. Independent sidebar New session creation remains unrelated, and same-file Edit from here remains valid because neither operation copies side context into a descendant. Durable side children do not prevent their ordinary parent from creating later independent side children. Same-file Edit from here and BranchNavigator operations remain allowed because they create branches inside the same durable side session rather than copying the side boundary into another session. If the selected safe prefix has no assistant message and native Pi therefore does not materialize the child file, `/side` reports that there is nothing safe to clone yet; it will not add unmaterialized-manager publication or custom persistence for that edge case.

Implementation should proceed through five coherent surfaces:

1. Add one server-safe pure side-session module for strict marker parsing, raw-branch ancestry, exact tool-batch cutoff selection, visible context/tree projection, and the fixed side policy/tool/extension identifiers. Keep message payloads out of diagnostics.
2. Extend the disposable extraction adapter with a distinct side operation that accepts only the captured cutoff ID, finalizes marker and name transactionally, reopens/verifies native identity and ancestry, and returns a typed bounded result. Leave existing clone behavior and result statuses unchanged.
3. Detect side identity before AgentSession service construction, install the loader prompt/extension override and SDK tool exclusion, retain immutable classification on the wrapper, add `/side`, and enforce terminal derivation plus marker-subtree navigation for both HTTP RPC and extension context actions.
4. Apply the shared projection/classification in root and context routes; carry bounded side/parent metadata through `useAgentSession`; let post-boundary live effects append only after canonical root establishment; keep HTTP repair authoritative; and preserve the existing complete-native-file Full history export as the explicit exception to ordinary transcript filtering.
5. Add exact `/side` handling during active and idle composition, prepare/activate the child through existing view transport, hide prohibited commands/actions, render the Return control, preserve manual Hide/Restore/permanent tree behavior, and update maintained documentation.

**Rough scope estimate:** touches a pure safe-cutoff/marker/projection module, the clone helper/result contract and transactional child finalization, wrapper `/side` handling plus side-session derivation/navigation guards, side-aware resource/tool construction, exact client command interception and ordinary session selection, side-aware transcript/tree/action projection, a small top-bar Return control, source retention, focused persistence/concurrency tests, and maintained clone/side-session documentation. Full history/export behavior is preserved and covered only by an intentional-exception regression. No cleanup subsystem is planned. Difficulty is high: native extraction, tree ancestry, selection, Hide, and hidden-source retention already exist, while snapshot-prefix validation, model-visible/UI-hidden context, and fail-closed capability filtering carry the main correctness burden.

## Comparable Product Findings

### Claude Code `/btw`

- Anthropic documents `/btw` as a one-response, dismissible overlay with full visibility into the current conversation, available while the main response is running. The question and answer never enter the main history.
- `/btw` has no tools and no follow-up turns. The user can press `f` to promote the exchange into a separate full session. It reuses the parent prompt cache.
- This is not implemented as an ordinary durable clone. Claude Code's public repository exposes release notes but not the product implementation, so only the documented behavior is authoritative here.
- Evidence: [Claude Code side-question documentation](https://code.claude.com/docs/en/interactive-mode#side-questions-with-btw) and [public `/btw` release history](https://github.com/anthropics/claude-code/blob/54cc51a08a5d3900e5abd02ad75a2ce46f3f008c/CHANGELOG.md#L2497-L2500).

### Codex `/side`

- Codex implements `/side` (and now `/btw` as an alias) as one ephemeral, multi-turn fork. The UI enters a side transcript while the parent remains active, exposes parent finished/failed/input/approval status, allows toggling back, and discards the side thread when it is closed or normal navigation leaves the parent/side pair.
- The side fork inherits the parent's current model, reasoning effort, service tier, permissions, cwd, and other active configuration, but sets `ephemeral = true`. Its inherited history remains model-visible but is hidden from the side transcript.
- Codex injects both hidden developer instructions and a side-boundary user item. They declare inherited requests and tool calls reference-only, prohibit subagents, prefer non-mutating inspection, and allow mutation only when the new side conversation explicitly requests it.
- This is **not** hard read-only enforcement. Codex copies the parent's permissions, approval policy, sandbox, cwd, and tool-capable configuration; `ephemeral = true` changes persistence, not filesystem authority. Mutation and subagent limits are model instructions, while any ordinary parent sandbox/approval checks still apply.
- Codex does not wait for a settled turn. Its current core snapshots whatever history is persisted and, if that history ends mid-turn, appends a synthetic interruption boundary **to the child only**. The source is not interrupted. Codex's own source notes that a true non-interrupting stable sampling-boundary snapshot is future work.
- Codex permits only one side conversation at a time, blocks nested `/side`, blocks it before the first conversation materializes and during review mode, limits available slash commands inside side mode, and accepts either bare `/side` or `/side <question>`.
- Evidence: [official Codex `/side` documentation](https://developers.openai.com/codex/cli/slash-commands#start-a-side-chat-with-side), [side lifecycle and guardrails](https://github.com/openai/codex/blob/6dc3ac8721366ce9912e3161af6779b90dc3a49c/codex-rs/tui/src/app/side.rs#L1-L56), [ephemeral configuration and hidden inherited transcript](https://github.com/openai/codex/blob/6dc3ac8721366ce9912e3161af6779b90dc3a49c/codex-rs/tui/src/app/side.rs#L558-L633), [inherited fork permissions and sandbox](https://github.com/openai/codex/blob/6dc3ac8721366ce9912e3161af6779b90dc3a49c/codex-rs/tui/src/app_server_session.rs#L1784-L1823), [fork/switch setup](https://github.com/openai/codex/blob/6dc3ac8721366ce9912e3161af6779b90dc3a49c/codex-rs/tui/src/app/side.rs#L656-L765), and [interrupted child snapshot semantics](https://github.com/openai/codex/blob/6dc3ac8721366ce9912e3161af6779b90dc3a49c/codex-rs/core/src/thread_manager.rs#L171-L199).

### Pi Web Implication

Neither competitor implements the chosen contract as a plain durable clone. Claude chooses a restricted one-shot overlay; Codex chooses a guarded ephemeral runtime with synthetic child-only boundary semantics. The chosen Pi Web behavior uses `/side` for a durable, named Pi session because that directly reuses Pi's native branch format, sidebar, refresh recovery, and existing source-retention behavior. Its workspace mutation policy intentionally matches Codex—ordinary authority plus explicit boundary instructions, not hard read-only enforcement—but Pi Web goes further on recurrence by removing known subagent and session-launching extensions from side runtimes.

## Constraints and Current Evidence

- The current `/clone` is a Pi-Web-owned exact built-in command. During an active run it is intercepted locally but returns **“Wait for the current run to finish before cloning”** rather than reaching the model.
- Current clone extraction reopens the persisted source on a disposable `SessionManager`, because `createBranchedSession()` mutates the manager on which it runs.
- Native Pi's `/clone` command can be dispatched while streaming, but it then replaces and aborts the source runtime; only its lower-level persisted branch primitive is reusable here.
- The source wrapper, source run, source live leaf, and source file must not be replaced, stopped, steered, or branched.
- This is exclusively a Pi Web host behavior. Do not modify the pinned Pi fork, native Pi `/clone`, `AgentSessionRuntime`, or native session-file semantics.
- A complete JSONL entry is not automatically a coherent conversational boundary. In particular, an assistant tool-call message can be persisted before its matching tool results; malformed/duplicate/foreign call-result IDs must fail normalization rather than count as completion.
- A first-turn source may have in-memory user input but no materialized file. Native `createBranchedSession()` also defers writing a child prefix with no assistant message. This edge case is explicitly out of scope: return the bounded nothing-safe-to-clone outcome and do not publish an unmaterialized manager or serialize Pi JSONL.
- The existing page-owned session view transport can retain the hidden active source until settlement after `/side` selects the child.
- The side child is a permanent ordinary session-tree node. Returning to the parent does not discard it; only the existing user-invoked Hide/Restore metadata changes its normal sidebar visibility.
- Side identity is reserved-marker state, never display-name inference. Malformed/duplicate/conflicting own-session markers and an active leaf outside the marker subtree fail closed. Direct context/navigation APIs must enforce the same boundary as the projected UI tree.
- Pi compaction remains available, but a side must keep its system policy after the marker is compacted out of immediate model context and must not render a potentially inherited-content-bearing compaction summary verbatim.
- Source and child share one cwd. The side keeps ordinary inspection and workspace authority but excludes known subagent/session-launch extensions. Its instructions discourage mutation unless explicitly requested after the boundary, but concurrent source/child writes remain possible and are not technically blocked.
- `excludeTools` can make known tool removal survive active-tool changes and reload, while a side-specific resource-loader extension override can remove whole launcher/delegation extensions, including their slash commands and natural-input handlers. The filter must classify loaded capabilities from bounded registered identities rather than user-facing session names or mutable filesystem assumptions.
- Unrestricted `bash` prevents this from being a security sandbox against deliberately scripted native-session creation. The supported hard invariant is that Pi Web and the known loaded delegation/launcher capabilities cannot derive a new session from a side.
- The existing Full history/export route intentionally remains a complete native-file view and may expose inherited entries. Ordinary chat/context/tree projection still starts after the boundary; this explicit export exception must not accidentally weaken those surfaces.
- Do not introduce a web-owned session-file format, speculative snapshot machinery, or a new persistence layer if Pi's existing safe persisted boundary is sufficient.
- Preserve unrelated working-tree changes, including the pre-existing modified clone plan.

## Telemetry / Debuggability

Use bounded server `/side` stage/outcome diagnostics for eligibility, strict tool-batch normalization, missing/unmaterialized source, extraction, marker append, naming, verification, cache publication, side-marker classification, capability filtering, and boundary-enforcement outcomes. Browser notices separately own creation-success-but-selection/hydration failure because selection occurs after RPC success; no acknowledgement protocol is added. Never log source messages, tool arguments/results, full paths, marker content, model payloads, or other private session data. No usage analytics are planned.

## Assumptions, Risks, and Blockers

- Exact trimmed `/side` is the decided command; inline arguments are not accepted, the interim `/btw` direction is superseded, and `/clone` remains unchanged.
- `/side` creates a durable ordinary multi-turn Pi child, immediately selects it, assigns `side-conversation-<timestamp>`, and leaves it in the ordinary session tree indefinitely. Returning through either the tree or the side-only top-bar button never discards it; existing manual Hide/Restore is the only removal-from-view workflow. It is intentionally not Claude's overlay or Codex's ephemeral thread. The targeted side child is terminal for Pi-Web-owned derivation: it cannot invoke nested `/side`, `/clone`, or Fork / New session; same-file Edit from here and BranchNavigator remain available only within the boundary subtree, independent New session creation remains unrelated, and the ordinary parent may create later sibling sides.
- The context boundary is computed from one invocation-time live-manager snapshot, not a tracked source watermark. During plain assistant streaming, retain the active user prompt as reference context and exclude the unpersisted partial assistant. An unmatched tool-call assistant message is removed with its whole result batch by cutting at its parent; no synthetic interruption or tool outcome is added. If the resulting prefix has no assistant message, `/side` is unavailable for that invocation.
- `/side` is eligible for idle sources and for sources active in prompt preflight, native model/tool work, extension command/UI work, or compaction whenever snapshot analysis finds a materializable safe prefix. It never waits for or changes the source lifecycle.
- Early first-turn invocation can have no eligible persisted prefix and may need a specific unavailable response.
- The child uses ordinary Pi Web inspection and workspace permissions except for a hard capability exclusion of known subagent and session-launching extensions. Source mutation remains technically possible through `bash`, `edit`, and `write`, and is allowed only after an explicit new side request.
- The boundary must prevent inherited source tasks from being treated as active work. Subagent/session-launch recurrence is both instructed against and capability-filtered; mutation is discouraged absent an explicit post-boundary request. Non-launching extensions remain available.
- Inherited safe-prefix messages remain in native/model context but are hidden from the side transcript and side branch-navigation surface. The boundary marker itself is also hidden. This is presentation filtering, not session-file truncation. Side compaction may summarize inherited context for the model, so the mandatory system policy survives independently and browser presentation replaces raw summary text with a generic notice.
- Generate names in UTC as `side-conversation-YYYY-MM-DDTHH-mm-ss-SSSZ`; the native session ID remains authoritative identity, so simultaneous equal display names are allowed rather than adding filesystem state or collision coordination.
- Full history/export is the intentional exception to transcript hiding: it remains unchanged and may render inherited entries because the user explicitly accepted complete history there.
